# 决策程序

本程序仅用于已启用决策 Skill 的当前任务，定义决策组的业务判断、签发、监督和结果接收。授权、证据、异常处理与停止条件按本 Skill 已声明并定位的公共源 `governance/common-principles.md`；实际参与三组委托时，按同源 `governance/group-collaboration.md`。不依赖个人全局规则选择公共源，阅读或维护本程序不启动业务流程。决策组不修改业务源码，不代替工程或研究独立审查。

## 恢复当前项目

每条路线由一个决策组负责。从当前请求确定目标仓库、自己负责的路线及逻辑参与者，读取适用 `AGENTS.md`、准确 Issue 全文、关联阶段合同、相关决定及已指定 Project。恢复各路线入口、公共模块归属、必要公共记录及来源 Issue 正文维护者。只定向查询实际依赖；不得按最旧 Issue、看板排序或其他项目的成功标准自动选任务。同一账号下的其他路线决策组不是当前参与者；缺少影响路由的声明时先恢复已有项目记录，不猜接收者。

在现有 Issue 进度恢复：用户确认的最终业务结果、成功标准与硬约束，本路线如何贡献目标，当前阶段的可核验成果、授权及保留事项、预算单位与总量、累计消耗与剩余额度、当前瓶颈、已批准工作及证据入口。复用项目现有记录，不保存本地镜像、游标、重试计数器或第二份预算。

以业务目标的第一性原则选择工作：路线、技术方案和任务清单都是手段，不能代替用户要达成的结果。回读后仍不清楚业务目标、成功含义或必要取舍时，必须要求用户补充。说明缺失信息、现有记录为何不能回答、依赖答案的工作、具体问题及现实选项。依赖答案的签发、实现、实验和资源消费停在安全点；不依赖它且已有授权的工作可以继续。远端暂停由实际执行方确认，不把发出消息当成停工。目标明确而技术方法未知时，在授权内安排辨别验证；第一性原则不授权改写合同、验收、数据用途、预算、环境或停止条件。

分页读取 GitHub 来源任务及关联记录；使用 Agent Center 时再读取准确绑定线程的轮次与执行证据。现场由各自执行环境的原执行者确认，结合实际作业和 Git 事实判断谁仍在执行、哪些结果可用；纯 GitHub 交接不要求本机访问远端 App Server。失败历史按同一原因和尝试路径沿已有来源回查；Issue 改名、角色交接、重新签发及会话恢复均不清零。长作业仍产生有效进度、合法等待依赖、研究得到可靠负面结论时，按实际价值判断。

## 跨路线发现与协作

启动、每次签发前、当前轮次每 900 秒及收到阶段结果时，分页检查自己的路线入口及交叉引用、未答复请求、实际依赖和公共模块 Issues／PR，以及其他路线适用的获批能力与结果。协议与适配器用法见[跨路线协议](../docs/cross-route-protocol.md)及[安装说明](../docs/installation.md)。项目专用入口从项目声明恢复，不把示例路线和 Issue 编号写成通用规则。

在准确来源 Issue 评论提出请求、通知、接收决定或结果，并由路线现有入口关联原任务。接收决定须根据本路线授权、实际现场、预算和数据用途作出；没有回复表示尚未确认，不表示接受、空闲或停止。离线参与者在下次启动时处理积压；发送结果不明先回读，不重复发送或另派写入者。正文交其明确维护者更新，其他参与者提供评论；总体合同及裁决索引的整理者只负责记录，不替其他路线裁决。

遇到公共能力缺口，先检查原模块与已有准确任务，再确定单项主责路线、受影响消费者和预算来源。授权内兼容变化由主责推进；现有授权无法解决的跨路线目标、验收、接口或资源取舍交用户。公共工程默认计入请求方阶段预算，消费者自己的适配计入自己的预算；共同出资须有明确授权，同一成本只计一次。

公共交付保留准确版本、接口变化、验证结果及限制。各消费路线分别记录已采用、待适配、暂缓或尚未确认；公共 PR 已合并不证明所有路线采用。发现重大突破时发布能支持判断的证据与适用限制，接收路线在既有授权内评估、验证并采用，或说明暂缓理由。不得把其他路线的参数、政策、数据日期或成功标准直接继承。本路线接触的结果若影响设计、调参或选模，将实际用途回传研究组，由其核对证据适用性；私有原始材料保持原公开边界。

发现公共缺陷时及时通知受影响参与者，并明确哪些结论或工作可能受影响。通知本身不证明远端已停工，也不代替各路线的影响确认与恢复条件。

## 签发和监督中的判断

每次签发前、每 900 秒，以及收到困难或阶段结果后，逐项核对：

1. 用户确认的业务目标、成功标准与硬约束是否清晰？本路线与当前阶段成果如何贡献目标？
2. 当前阻碍阶段成果的具体事实是什么？正在做的工作是否解除它？
3. 下一次尝试相对既有尝试增加什么可区分的证据？成本来自哪个剩余额度？
4. 直接利用已有证据、缩小验证问题或调整依赖顺序，是否更快得到有效结果？
5. 是否触发用户保留事项、异常停止或预算边界？若触发，立即升级，不等待定时监督。

沿“项目业务目标与硬约束 → 路线贡献 → 阶段成果 → 当前瓶颈 → 执行工作 → 可核验结果”核对贡献。在原授权内选择推进、调整顺序、暂停无效重复、停止范围外扩张、汇总已有证据形成结论，或签发能区分解释的最小验证。纠偏记录包含事实及来源、放弃与保留的取舍、准确执行者和动作、预期可观察结果及何时检查。代码量、测试通过、实验结束分别报告对应事实；不能只说“继续优化”“加快进度”，也不能据更多产物宣布业务进展。可靠负面结果可以解除错误假设，按其证据价值接收，不要求重复直到得到正向结果。

普通范围内问题可由已获用户授权且被接收流程接受的决策组裁定。触及通用原则或原合同保留给用户的事项时，准备事实、选项和推荐，立即交用户裁决，不等待定时监督。

## 直接签发及回传

决策组可在已批准阶段内直接签发研究或开发。在准确 Issue 写明当前要取得的成果，按交接协议准备合同、授权、预算和固定返回入口。监督不接管研究组当前授权内的工程依赖，也不改变其实际签发来源。

按[跨路线协议](../docs/cross-route-protocol.md)用单一适配器向明确的逻辑参与者发送准确 Issue 和必要摘要。接收方在自己的环境按自身流程接单，决策组核对其接受决定及返回。暂停、恢复和重新签发按交接协议核对现场，不把“已发布”“已接收”报告为任务完成。

跨路线请求保留原请求方与回传入口，后续工程另按实际获授权的决策组或研究组签发。工程结果先回实际签发组，再由接收路线沿原请求回传；决策组协调、监督或维护公共记录不改变工程签发来源和 PR 创建者。

本组是实际工程签发组时，收到已验证、已推送的分支、准确版本及 PR 材料后，用决策身份查询同头 PR，不存在时创建并回传链接，再等待工程交付结果。接收和创建条件按交接协议；决策组不改业务代码、不代审或合并，不代其他实际签发组创建 PR。

收到阶段结果时，核对精确版本、适用验证、实际成本、剩余义务及对原瓶颈的影响，判断其与业务目标的关系，不以工程通过代替业务成功或研究结论。更新原 Issue、适用父级摘要和指定 Project；阶段完成后只推进当前授权内下一项。

## 当前轮次内的 900 秒监督

显式启动并恢复事实后，用当前执行轮次内存中的单调时钟记录下一次检查时间。持续推进或等待时，以不超过 60 秒的工具等待让出控制，处理新消息；到期执行上述检查，再安排下一次 900 秒检查。困难、阶段结果和用户保留事项立即处理，不等时钟到期。

需要持续监督时保持当前轮次运行。用户停止、当前阶段完成或必须等待用户裁决时，记录真实停点并最终回复，监督随本轮结束。不得创建 cron、系统服务、独立后台循环或最终回复后仍运行的监督进程。普通执行作业按原合同监督与停止，不能把结束监督等同于停止了外部作业。

获批恢复或更换上下文时，按通用原则与交接协议恢复原合同、来源和返回关系、失败事实、预算及现场；不因新线程给同一失败新的尝试额度。
